# Profile-attestation production configuration checklist

Everything the profile-attestation signer (`workers/api/src/profileAttestationSigning.ts`) needs to go from
"correctly fails closed because it isn't configured" to "signs in production", and nothing more. This is an
**interim, single-trusted-key** setup (see `docs/attestation-profile-design.md` §10.1-§10.3) — it does not (and
must not yet) claim key-state history, retirement/revocation, a monotonic sequence, or rollback detection.

This document contains **no secret values**. It never will: a production private key must never be committed
to this repository, written into any tracked file, or generated by `workers/api/scripts/generate-dev-profile-
attestation-key.mjs` (that script is explicitly DEV-ONLY — see its own header — and is never invoked by any
build, test, or deploy script; confirmed by `grep`, not by convention alone).

## Required configuration

| Variable | Secret? | Where | Status as of this checklist |
|---|---|---|---|
| `PROFILE_ATTESTATION_SIGNING_PRIVATE_KEY_JWK` or `_JWK_B64` | **Yes** | `wrangler secret put` | Not yet set (step 1-2 below) |
| `PROFILE_ATTESTATION_ISSUER` | No | `wrangler.toml` `[vars]` | Set: `agentverify-profile-prod` |
| `PROFILE_ATTESTATION_KEY_PURPOSE` | No | `wrangler.toml` `[vars]` | Set: `agentverify-profile-v1` (fixed protocol constant, not a choice) |
| `PROFILE_ATTESTATION_EXPECTED_KEY_ID` | No (not secret — it's the same value the public route publishes) | `wrangler.toml` `[vars]`, added later | Deliberately unset until step 4 |

All four are read only by `workers/api/src/profileAttestationSigning.ts` — see its own doc comment for the exact
refusal behavior when any is missing or wrong (fails closed to HTTP 503, never a silent unsigned success; see
`docs/attestation-profile-design.md`'s metering/signing sections and `workers/api/test/profileAttestationSigning
.test.mjs` for the tested contract). There is no insecure default for issuer, purpose, or key: all three of the
env-driven checks (`!env.PROFILE_ATTESTATION_ISSUER`, `PROFILE_ATTESTATION_KEY_PURPOSE !== PROFILE_KEY_PURPOSE`,
absent private key) refuse rather than assume a value.

## Steps

1. **Generate the production key pair OUTSIDE this repository**, using whatever secure process your
   infrastructure already uses for signing-key custody (a KMS, an HSM, or at minimum an offline, audited
   generation step) — not `generate-dev-profile-attestation-key.mjs`, which is a throwaway-key convenience tool
   for local development only. The key must be ECDSA P-256. If your custody solution can hold the key
   non-exportable and expose only a signing capability, prefer that over ever having the raw JWK touch this
   Worker's environment at all (see `profileAttestationSigning.ts`'s own header — the module boundary here
   exists specifically to make that swap possible later without touching any caller).

2. **Provision the private key as a Worker secret**, never a plaintext `[vars]` entry:
   ```bash
   wrangler secret put PROFILE_ATTESTATION_SIGNING_PRIVATE_KEY_JWK --config workers/api/wrangler.toml
   ```
   (or `_JWK_B64` with the same JSON, base64-encoded, if your deployment pipeline handles base64 more reliably
   than a multi-line prompt — both are read identically by `resolveJwkJson`). Paste the JWK when prompted;
   `wrangler secret put` does not echo it and does not write it to any file this repository tracks.

3. **Confirm `PROFILE_ATTESTATION_ISSUER` and `PROFILE_ATTESTATION_KEY_PURPOSE`** are present in
   `workers/api/wrangler.toml`'s `[vars]` block (already committed as part of this checklist: `agentverify-
   profile-prod` and the fixed `agentverify-profile-v1`). Change the issuer string here if a different label is
   wanted — it is a non-secret display value, safe to edit and redeploy.

4. **Deploy, then derive and publish the key's identity.** After `wrangler deploy`, call
   `GET /v1/profile-attestation/public-key` on the deployed Worker. It returns `{issuer, keyId, publicKey:
   {kty,crv,x,y}, algorithm, purpose}` for the key just provisioned (structurally guaranteed to match, since
   `keyId` is always derived from the same key `signProfileAttestation` signs with — see that module's own doc
   comment). Take the `keyId` from that response and:
   - Publish it (and the public JWK) somewhere under Agent Verify's own control, independent of this route —
     e.g. the Agent Verify website or docs — so a third party has a channel to obtain it that does not depend
     on trusting any single bundle or this route alone. **This publication is the trust anchor a signature is
     checked against — never a bundle's own embedded `publicKey`.**
   - Add `PROFILE_ATTESTATION_EXPECTED_KEY_ID = "<that keyId>"` to `wrangler.toml`'s `[vars]` and redeploy. From
     then on, a misconfiguration that would sign under an unexpected key (a wrong secret pasted, a rotated key
     applied without updating this value, etc.) refuses closed (`key-identity-mismatch`, 503) instead of
     silently signing under a different identity than what was published.

5. **Verify before announcing the feature**: confirm `GET /v1/profile-attestation/public-key` returns 200 with
   no `d` member anywhere in the response, and that a real `attest: true` request now returns 200 with a
   signed `attestation` whose `publicKey`/`keyId` match what was published in step 4.

## What this interim setup does and does not provide

Once the steps above are complete, a third party can: retrieve the published key independently (step 4),
compare a bundle's embedded `publicKey`/`keyId` against it, verify the signature, and conclude the bundle was
genuinely issued by Agent Verify (issuer/key provenance) with the exact assessment/package/profile binding the
signature covers. It does **not** yet provide key-state history, retirement/revocation semantics, a monotonic
key-set sequence, or rollback detection — none of those exist in this release, and nothing in the response
shapes above (`getProfileAttestationPublicKeyInfo`'s five fields) claims them. Do not add `sequence`,
`keySetVersion`, `generatedAt`, or a `status` field to that response until the real key-set publisher
(`docs/attestation-profile-design.md` §10.2) exists — faking any of them would be worse than the current honest
omission.
